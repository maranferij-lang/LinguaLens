# Безпека LinguaLens

Що вже закрито, які ризики лишились і що перевіряти перед кожним релізом.

Головна думка архітектури: **нам нема чого втратити, крім грошей на AI**.
Паролів, пошти й імен немає. Словник і прогрес не залишають телефон, доки
людина сама не увійде через Apple (v1.1): тоді вони лежать на сервері,
прив'язані до Apple ID, і це друге, що треба берегти, — чужий словник не має
прочитати, переписати чи стерти ніхто, крім власника. Решта захисту — про
те, щоб ніхто не палив наш AI-ключ безкоштовно.

---

## Закрито

### Ключі
- Ключі AI і секретний ключ RevenueCat живуть **лише на сервері**
  (`server/.env` локально, змінні або Secret Manager у Cloud Run, див.
  `DEPLOY.md`). Застосунок не знає жодного.
- Усе з префіксом `EXPO_PUBLIC_` вшивається в застосунок, тому там лише
  публічне: адреса сервера, публічний ключ RevenueCat `appl_…`, посилання.
- `.gitignore` закриває `.env`, `server/.env`, `server/data.json`, `*.p8`,
  `*.p12`, `*.key`, `*.mobileprovision`, `credentials.json`; `.gcloudignore`
  не пускає `.env` у хмару.
- Ключ Gemini передається заголовком `x-goog-api-key`, а не в URL, тож не
  осідає в логах проксі.

### Немає чого красти
- Реєстрацію, вхід за паролем і редагування профілю на сервері прибрано
  (`/auth/register`, `/auth/login`, `PATCH /me` відповідають 404). Пароль не
  витече, бо його немає.
- Сервер знає про пристрій лише: випадковий id, seed для слова дня, довічні
  лічильники сканів і сцен, дату закінчення Pro і відповіді онбордингу
  (`profile`: цілі, сфера, рівень 1–10, звідки дізнались). Профіль — лише
  варіанти з готових списків: невідоме значення сервер відкидає, вільного
  тексту там не буває, тож особисті дані туди не потраплять навіть з
  підробленого запиту.
- Якщо людина увійшла через Apple — ще й словник (слова, переклади, приклади,
  розклад повторень), лічильники досягнень і графік активності. Від Apple
  беремо тільки стабільний `sub` і зберігаємо не його, а HMAC від нього;
  пошту й ім'я не просимо. Для відкликання входу — refresh-токен Apple.
- Кадр із камери йде в AI і **не зберігається** на сервері та не пишеться в
  логи. Вирізана наліпка лишається тільки на телефоні: синхронізація бере
  поля слова за білим списком, фото, контур і рамка на сервер не потрапляють.
- У логах немає особистих даних: провайдер, пара мов, час, розпізнане слово.
  Токени Apple, коди й `sub` не пишуться ніколи — лише причина відмови.

### Токени пристроїв
- `base64url(payload).HMAC-SHA256(AUTH_SECRET)`, перевірка через
  `timingSafeEqual`. Без залежностей.
- На телефоні лежать у Keychain (`AFTER_FIRST_UNLOCK`), а не в AsyncStorage.
  Keychain переживає перевстановлення, тож новий id «з нуля» так не отримати.
- «Стерти всі мої дані» (`DELETE /me`) видаляє запис, і старий токен одразу
  стає недійсним. Для акаунта з Apple — ще й словник, зв'язок з Apple ID і
  сам вхід через Apple (відкликання, див. нижче). У відповіді лишається тільки
  `carry` — підписані лічильники сканів і проби сцени, без id і без нічого
  особистого (див. «Пристрої можна фармити»).
- Токени зі службовим призначенням (nonce для входу через Apple, `carry`)
  підписані тим самим секретом, але як токен пристрою не приймаються.

### Вхід через Apple і синхронізація (v1.1)
**Підробка й повтор токена.**
- identityToken перевіряється підписом RS256 ключами з JWKS Apple, а також
  `iss`, `aud` (лише наш bundle id, `APPLE_AUDIENCES`), `exp` (60 с запасу на
  годинники) і `iat` не з майбутнього. Інші алгоритми (`HS256`, `none`)
  відкидаються ще до перевірки підпису.
- Nonce: сервер видає підписаний `AUTH_SECRET` nonce, прив'язаний до id
  пристрою і живий 10 хвилин; застосунок віддає Apple його SHA-256, Apple
  вшиває хеш у токен, сервер звіряє обидва. Перехоплена пара «токен + nonce»
  не годиться з іншого пристрою (чужий uid) і після 10 хвилин. Nonce без стану,
  тож у межах 10 хвилин той самий пристрій може повторити той самий вхід, але
  це лише ідемпотентно повторює результат.
- JWKS кешується на 6 годин; невідомий `kid` (Apple змінив ключі) — один
  перепит, але не частіше разу на хвилину: підробні токени з випадковими
  `kid` не перетворюють сервер на генератор запитів до Apple. Тайм-аут 5 с.
  Apple недоступний — `503 APPLE_UNAVAILABLE`, а не «поганий токен»; ключ,
  відомий зі старого кешу, приймаємо й тоді.
- Помилки входу — `400 APPLE_INVALID`, ніколи не 401: на 401 застосунок
  вважає, що пристрій забуто, і скидає ідентичність.

**Захоплення акаунта.**
- Перейти в чужий акаунт можна лише з дійсним identityToken саме цього Apple
  ID, виданим на nonce саме цього пристрою. Інших шляхів (за id, за токеном
  іншого пристрою) немає.
- Зв'язок — документ `appleAccounts/<HMAC(AUTH_SECRET, sub)>`, створюється
  умовно («лише якщо ще немає»). Два телефони, що входять одночасно, не
  отримують двох акаунтів і не переписують зв'язок один одного: другий
  перечитує його й переходить в акаунт першого (тест у
  `server/test/apple.test.js`). Замінити зв'язок можна, лише коли акаунт, на
  який він указує, уже стерто, і теж умовним записом.
- Пристрій, уже прив'язаний до іншого Apple ID, не переписується й не
  стирається: для нового Apple ID заводиться окремий акаунт. Анонімний запис,
  що перейшов в акаунт, стирається, і його токен одразу недійсний.
- `authorizationCode` міняється на refresh-токен лише якщо `sub` у відповіді
  Apple збігся з перевіреним токеном: підкладений код чужого входу не дасть
  видаленню нашого акаунта відкликати вхід іншої людини.

**Зловживання синхронізацією.**
- `/sync` — лише для акаунта, на який зараз указує зв'язок Apple ID
  (`403 SIGN_IN_REQUIRED`); перевіряється на кожен запит.
- 60 запитів на хвилину з IP і окремо на акаунт; тіло до 1 МБ; до 500 слів у
  запиті, до 6000 живих слів в акаунті й до мільйона символів документа
  (`413 DICT_FULL`; ліміт документа Firestore — 1 МіБ).
- Поля слова — за білим списком, рядки обрізані до довжин картки, id лише
  `[A-Za-z0-9_-]{1,40}`, дати активності — справжні календарні дні. Усередині —
  `Map`, тож id `__proto__` лишається просто id.
- Час зміни з майбутнього обрізається до серверного «зараз»: телефон, чий
  годинник поспішає, не робить свої правки непереможними.
- Запис умовний за версією документа з повтором: дві синхронізації одночасно
  не затирають одна одну. Розпаковка документа обмежена 64 МБ.
- Вхід: 30 запитів (nonce і вхід разом) за 10 хвилин з IP.

**Видалене не воскресає.** Видалення ходять надгробками, і сервер прибирає їх
через 60 днів. Найбільший `rev` прибраних надгробків документ пам'ятає
(`prunedRev`). Телефон, чий `since` менший за нього (не синхронізувався
довше, ніж живуть надгробки), отримує не зміни, а весь словник із
`reset: true, stale: true`: частковою відповіддю видалення, яких сервер уже
не пам'ятає, не передати. На `stale` застосунок звіряє словник — прибирає
синхронізовані й не змінені слова, яких у відповіді немає, і надсилає лише
свої зміни. Звичайний `reset` (`since` 0 або більший за `rev` — сервер
втратив дані) означає інше: надіслати своє заново. `stale` буває лише разом
із `reset`.

**Видалення акаунта.** `DELETE /me` стирає зв'язок (лише якщо він досі наш),
словник, запис і ще раз словник — синхронізація, що саме писала, могла
встигнути між ними; синхронізація, що створила словник уже після видалення,
сама його прибирає. Потім відкликає вхід у Apple (`/auth/revoke`), якщо
налаштовано ключ `.p8`; невдача відкликання не скасовує видалення.

### Ліміти й гроші на AI
- **Ліміт сканів довічний і його рахує сервер** — у записі (`users/<id>.scans`,
  анонімний пристрій чи акаунт Apple), а не в телефоні, і перевіряє **до**
  виклику AI (`402 SCAN_LIMIT`). За замовчуванням — **один безкоштовний скан
  на все життя запису** (`FREE_SCANS`), не на день: кожен виклик AI коштує
  грошей. Раніше лічильник жив у телефоні й обнулявся перевстановленням, потім
  був денним і щоночі давав новий скан. Скани в Pro теж рахуються (наперед
  невідомо, чи людина має Pro), тож Pro, що скінчився, безкоштовного скану
  вже не має. Записи часів денного ліміту несуть старий лічильник
  `usage.scans` — береться більший з двох, сам `usage` більше не пишеться.
- **Скан цілої кімнати (сцена) — Pro** з довічною пробою: `FREE_SCENES` сцен
  на запис (за замовчуванням одна). Сцена забирає і безкоштовний скан. Спершу
  ліміт сканів, потім проба (`402 SCENE_PRO`) — обидва до виклику AI. Скан і
  сцена займаються **одним** умовним записом (версія документа) і так само
  разом повертаються, якщо скан не вдався (422, 502, 504, виняток, людина не
  дочекалась), ніколи нижче нуля: паралельні скани й сцени не проходять повз
  ліміт, а невдалий скан не з'їдає ні скан, ні пробу (тести гонок — у
  `server/test/lifetime.test.js`, `billing.test.js` і `scenepro.test.js`,
  зокрема зі сховищем, що відповідає із затримкою, як Firestore).
- Pro перевіряється ліниво: RevenueCat питаємо, лише коли безкоштовне
  скінчилось (скан чи проба сцени), і не частіше, ніж дозволяє кеш на
  10 хв. Безкоштовний скан не коштує жодного запиту до RevenueCat.
- Тіло `/scan` (до 4 МБ) читається до того, як займається слот: від `mode`
  залежить, що саме рахувати. Відмова 402 однаково приходить до виклику AI,
  а погане тіло дає 400, не торкаючись лічильників.
- Ліміти з оточення — лише цілі ≥ 0. Опечатка (`FREE_SCANS=три`) раніше
  давала `NaN` і безлімітні безкоштовні скани; тепер сервер пише попередження
  й бере значення за замовчуванням. Стара `FREE_SCANS_PER_DAY` нічого не
  відкриває: сервер її ігнорує й пише про це в лог при старті.
- Ліміт частоти: `RATE_PER_MIN` (20) сканів і запитів «слова дня» на хвилину з IP
  (GET і POST разом). Персональне слово дня (`POST /word-of-day`) ще й
  `RATE_PER_MIN` на пристрій: кожен запит — до 14 перекладів, а теми й «Знаю»
  обирає клієнт. Переклади кешуються (`wordCache`), тож перебір усіх тем
  коштує один виклик AI на слово, а не на запит.
- `POST /me/profile`: 20 на хвилину з IP і 10 на пристрій.
- Створення пристроїв: **20 на годину з IP**. Достатньо для гуртожитку за
  одним NAT, але не для скрипта, який фармить безкоштовні скани.
- Справжня IP: береться запис `X-Forwarded-For`, який дописав проксі Cloud Run
  (правий, `TRUST_PROXY_HOPS`), а не перший, який пише сам клієнт. Раніше
  підміною заголовка обходились усі ліміти.
- Локальна дата клієнта (`x-local-date`) приймається лише в межах ±1 доби від
  серверної; вигадана далека дата ігнорується. На ліміт сканів вона більше не
  впливає взагалі: він довічний, і жодна дата (ні «завтра», ні серверний
  годинник, переведений на рік уперед) його не повертає — це тести в
  `server/test/lifetime.test.js` і `api.test.js`. Дата лишилась для слова
  дня й поля `day` у відповіді.

### Підписка
- Pro для сканів визначає **сервер**, а не телефон: вебхук RevenueCat
  (`/webhooks/revenuecat`) і, якщо вебхук загубився, власний REST-запит до
  RevenueCat із кешем на 10 хв.
- Пароль вебхука (`REVENUECAT_WEBHOOK_AUTH`) порівнюється за сталий час. Без
  заданого пароля вебхук завжди відповідає 401.
- Перенесення покупки (`TRANSFER`) забирає Pro у попереднього id; повернення
  коштів через підтримку Apple знімає Pro одразу.
- У релізній збірці без ключа RevenueCat покупки **вимкнені** (режим
  `unavailable`), а не імітуються: Pro безкоштовно ніхто не отримає.

### Стійкість сервера
- `SECURITY_HEADERS` раніше не був оголошений, і сервер **падав на першому ж
  запиті**. Виправлено.
- Кожен обробник загорнутий у `catch`: виняток дає 500, а не вбиває процес
  разом із запитами інших людей.
- Розміри тіл: `/scan` до 4 МБ (застосунок шле 150–400 КБ), вебхук до 64 КБ,
  `POST /word-of-day` до 64 КБ (500 «Знаю»), `/me/profile` до 4 КБ; більше
  дає 413. Битий JSON дає 400.
- Відповідь моделі вважається недовіреною: поля обрізаються за довжиною,
  координати рамки й контуру затискаються в 0–1000, вирази для просунутих
  (`extras`) — лише пари рядків, до трьох, 60/80 символів.
- Усе, що приходить у запиті слова дня й профілю, чиститься (`server/profile.js`):
  цілі й сфери лише з переліку, рівень — ціле 1–10, дати — справжні
  календарні дні не пізніше «сьогодні», «Знаю» — до 500 рядків по 60
  символів. Мови перевіряються через `Object.hasOwn`, тож `constructor` чи
  `__proto__` не потрапляють ні в підказку моделі, ні в ключ кешу.
- Помилки Gemini/Anthropic лишаються в логах; клієнт отримує загальне «AI
  тимчасово недоступний», без деталей інфраструктури.
- Заголовки на кожній відповіді: `nosniff`, `X-Frame-Options: DENY`,
  `no-referrer`, HSTS, `Cache-Control: no-store`.

### Firestore
Сервер ходить у Firestore від імені сервісного акаунта Cloud Run (IAM).
Поки проєкт не підключений до Firebase, прямого доступу з клієнтів немає
зовсім. Якщо колись підключиш — одразу правила `allow read, write: if false;`
(готовий текст у `DEPLOY.md`, крок 3). Це стосується й нових колекцій v1.1:
`appleAccounts` (зв'язки Apple ID) і `dicts` (словники).

## Лишається як свідомий ризик

### `APP_TOKEN` — лише «лежачий поліцейський»
Він лежить у бінарнику, і витягнути його можна за вечір. Він відсікає
випадкових ботів, які знайшли URL, але не цілеспрямовану людину. Справжній
захист — ліміти за id і за IP.

### Пристрої можна фармити
Кожен новий запис дає один безкоштовний скан на все життя і одну пробу сцени.
Зараз це стримують 20 нових пристроїв на годину з IP і Keychain, але з пулом
проксі можна наробити багато id.

**«Стерти всі мої дані» нового скану не дає.** `DELETE /me` стирає запис, а у
відповіді віддає `carry` — лічильники сканів і проби сцени з підписом, без id
і без нічого особистого (`auth.carryToken`). Застосунок несе його в нову
ідентичність, як токен при виході (`eraseServerData` → `startOver({ carry })`
у `src/auth.js` → `POST /auth/device { previous: carry }`), і новий запис
починає з тими самими лічильниками. Без цього стирання щоразу дарувало б скан,
а в акаунті Apple ще й нічого не коштувало б: вийти, стерти гостя (акаунт це
не чіпає), сканувати, увійти назад — і синхронізований словник знову на місці.
Підробити чи зменшити `carry` не можна (HMAC). Скрипт, що його не несе,
отримує чисту ідентичність — але це той самий фарм пристроїв, що й вище.
Сервер, який уже забув пристрій (`401` на `DELETE /me`), `carry` не дає — тоді
новий запис з нуля (так само після зміни `AUTH_SECRET` чи стирання акаунта з
іншого iPhone: ціна — увесь акаунт). Решта стирання — по-справжньому
(приватність і GDPR): запис, словник, зв'язок з Apple ID, а на телефоні слова,
фото наліпок, прогрес і «Знаю». Перевстановлення нового скану **не** дає:
токен лежить у Keychain і переживає видалення застосунку, а `ensureSession`
після перевстановлення питає `GET /me` і лишається в тому самому записі.

Вихід з акаунта й вхід знову нового скану чи проби не дають. Застосунок при
виході шле старий токен (`POST /auth/device { previous }`), і сервер переносить
довічні лічильники сканів і сцен у нову анонімну ідентичність. Без мережі (чи
коли відповідь загубилась) старий токен чекає в Keychain окремо від токена
сесії (`ll_carry`) і йде з наступною спробою, хоч і після перезапуску; сесії
він не повертає — сервер бере з нього лише лічильники, — а прибирається,
щойно сервер видав новий запис. Так само чекає й `carry` стирання.

Вхід через Apple в існуючий акаунт зливає лічильники телефона з акаунтом: і
скани, і сцени — більше з двох (не сума: це той самий телефон, що ходить туди
й назад; старий денний `usage.scans` теж рахується). Новий акаунт для іншого
Apple ID теж бере лічильники телефона. Скрипт, що не шле `previous`, отримує
чисту ідентичність — але це той самий фарм пристроїв, що й вище.

**Що далі:** **App Attest / DeviceCheck** — Apple підтверджує, що запит іде
зі справжнього iPhone і нашого застосунку, а не зі скрипта. Це наступний
крок, якщо витрати на AI почнуть рости швидше за кількість людей.
Простіший запобіжник — загальна денна стеля безкоштовних сканів на весь сервер.

### Токен Pro-пристрою можна винести
Людина з jailbreak може дістати токен свого Pro-пристрою і сканувати з
нього скриптом без ліміту (його стримує лише `RATE_PER_MIN` на IP).
**Варто:** жорстка денна стеля і для Pro (напр. 300 сканів на пристрій) —
справжня людина до неї не дійде.

### Токени не відкликаються поштучно
Анонімний токен вартий стільки, скільки сам запис. У безкоштовного це один
чужий скан на все життя (найпевніше вже витрачений). Але Pro прив'язаний до id
запису (appUserID у RevenueCat), а вхід через Apple необов'язковий, тож
більшість покупок — саме на анонімних id: украдений токен підписника дає
безлімітні скани Pro за наш рахунок (стримує лише `RATE_PER_MIN` на IP, як у
розділі вище) і `DELETE /me` — стерти чужий запис. Токен акаунта з Apple ще
й дає читати й міняти синхронізований словник. «Вийти» в застосунку лише
забуває токен на телефоні, а сам токен дійсний і далі; повністю його знецінює
тільки «Видалити акаунт». Витягти токен можна лише з Keychain розблокованого
телефона (чи з jailbreak), тож ризик прийнятний.
**Що далі:** версія токенів у записі — тоді «вийти всюди» стане одним
записом; денна стеля для Pro (розділ вище) обмежить украдений токен
підписника; App Attest — запит без нашого застосунку на справжньому iPhone
нічого не дасть навіть із чужим токеном.

Єдиний загальний «рубильник» — зміна `AUTH_SECRET`: вона знецінює **всі**
токени, і кожен пристрій тихо отримає нову ідентичність (лічильники
скинуться, Pro повернеться через «Відновити покупки»). Але `AUTH_SECRET` —
ще й ключ HMAC зв'язків Apple ID: після зміни вхід через Apple не знайде
жодного старого словника (дані на місці, але осиротілі). Тому `AUTH_SECRET`
після релізу **не міняємо**.

### Ліміт мов — у телефоні
Стелі словника більше немає. 1 мова перевіряється на пристрої, і на jailbreak
її можна обійти. Це свідомо: вона нам нічого не коштує. Усе, що коштує грошей (скани), — на
сервері. Синхронізація теж не питає про Pro: будь-який акаунт з Apple може
зберегти до 6000 слів — це один документ до мегабайта, копійки.

### Межі синхронізації «пізніша зміна перемагає»
- Порядок змін визначає годинник телефона. Час із майбутнього сервер
  обрізає, але телефон, чий годинник **відстає**, програє свіжішим правкам
  з інших телефонів.
- Надгробки (видалені слова) живуть 60 днів від того, як їх отримав сервер.
  Телефон, що був офлайн довше й досі має стерте слово, поверне його, якщо
  надішле це слово знову.
- Лічильники досягнень між телефонами зливаються максимумом, а не сумою:
  повтор запиту нічого не подвоює, але й квізи з двох телефонів не
  додаються.
- Refresh-токен Apple лежить у Firestore як є. Без нашого ключа `.p8`
  (Secret Manager) він нічого не дає: Apple приймає його лише разом із
  client_secret, підписаним цим ключем.
- Невдале відкликання при видаленні акаунта не повторюється — лишається
  рядок у лозі. Людина може прибрати LinguaLens зі списку «Вхід через Apple»
  в налаштуваннях Apple ID сама.

### Інше, не критично
- **`Access-Control-Allow-Origin: *`.** Для мобільного застосунку не
  проблема (Origin не надсилається, credentials через `*` не проходять).
  Коли з'явиться веб-версія — звузити.
- **Немає моніторингу.** Різкий стрибок сканів означає або вірусний ріст, або
  зловживання. Мінімум — бюджетний алерт у Google Cloud (`DEPLOY.md`, крок 10),
  далі Sentry і алерт на кількість `/auth/device` за годину.
- **Ліміти частоти в пам'яті одного інстансу.** Якщо Cloud Run підніме кілька
  інстансів, кожен рахує окремо. Для поточних масштабів нормально.

## Перевірка перед кожним релізом

```bash
cd ~/Documents/LinguaLens

# 1. Жодного ключа в коді застосунку (має бути порожньо)
grep -rnE "AIza|sk-ant-|sk_[A-Za-z0-9]{16,}" App.js src/ .env.example

# 2. Секрети не відстежуються git (має бути порожньо)
git ls-files | grep -E '(^|/)\.env$|\.p8$|\.p12$|server/data\.json$'

# 3. У змінних збірки лише публічне (немає sk_, AIza, sk-ant-)
eas env:list production

# 4. Тести
npm test && npm run test:server
npm audit --omit=dev

# 5. Живий сервер
URL=https://lingualens-server-….run.app
curl -s -D - -o /dev/null $URL/health | grep -iE "strict-transport|nosniff"   # заголовки на місці
curl -s -X POST $URL/scan -H 'x-app-token: ТВІЙ_APP_TOKEN'                  # → {"error":"UNAUTHORIZED"}
curl -s -o /dev/null -w "%{http_code}\n" -X POST $URL/webhooks/revenuecat -d '{}'  # → 401
curl -s $URL/health                                                          # → "store":"firestore"

# 6. Вхід через Apple і синхронізація (тимчасовий пристрій, наприкінці стираємо)
H='x-app-token: ТВІЙ_APP_TOKEN'
T=$(curl -s -X POST $URL/auth/device -H "$H" | sed -E 's/.*"token":"([^"]+)".*/\1/')
curl -s -X POST $URL/sync -H "$H" -H "authorization: Bearer $T" -d '{}'          # → {"error":"SIGN_IN_REQUIRED"}
curl -s -X POST $URL/auth/apple -H "$H" -H "authorization: Bearer $T" -d '{}'    # → {"error":"APPLE_INVALID"}
curl -s -X POST $URL/me/profile -H "$H" -H "authorization: Bearer $T" -d '[]'    # → {"error":"BAD_JSON"}
curl -s -X DELETE $URL/me -H "$H" -H "authorization: Bearer $T"                   # → {"ok":true}
gcloud run services logs read lingualens-server --region europe-central2 --limit 200 \
  | grep APPLE_PRIVATE_KEY                                                    # має бути порожньо
```

І в браузері: [Billing → Budgets & alerts](https://console.cloud.google.com/billing)
— бюджет із попередженням виставлений.

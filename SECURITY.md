# Безпека LinguaLens

Що вже закрито, які ризики лишились і що перевіряти перед кожним релізом.

Головна думка архітектури: **нам нема чого втратити, крім грошей на AI**.
Акаунтів, паролів, пошти й імен немає; словник і прогрес не залишають
телефон. Тож більшість захисту — про те, щоб ніхто не палив наш AI-ключ
безкоштовно.

---

## Закрито

### Ключі
- Ключі AI і секретний ключ RevenueCat живуть **лише на сервері**
  (`server/.env` локально, змінні або Secret Manager у Cloud Run, див.
  `DEPLOY.md`). Застосунок не знає жодного.
- Усе з префіксом `EXPO_PUBLIC_` вшивається в застосунок, тому там лише
  публічне: адреса сервера, публічний ключ RevenueCat `appl_…`, посилання.
- `.gitignore` закриває `.env`, `server/.env`, `server/data.json`, `*.p8`,
  `*.p12`, `*.key`, `*.mobileprovision`, `credentials.json`; `.gcloudignore`
  не пускає `.env` у хмару.
- Ключ Gemini передається заголовком `x-goog-api-key`, а не в URL, тож не
  осідає в логах проксі.

### Немає чого красти
- Реєстрацію, вхід за паролем і редагування профілю на сервері прибрано
  (`/auth/register`, `/auth/login`, `PATCH /me` відповідають 404). Пароль не
  витече, бо його немає.
- Сервер знає про пристрій лише: випадковий id, seed для слова дня, лічильник
  сканів за сьогодні, дату закінчення Pro.
- Кадр із камери йде в AI і **не зберігається** на сервері та не пишеться в
  логи. Вирізана наліпка лишається тільки на телефоні.
- У логах немає особистих даних: провайдер, пара мов, час, розпізнане слово.

### Токени пристроїв
- `base64url(payload).HMAC-SHA256(AUTH_SECRET)`, перевірка через
  `timingSafeEqual`. Без залежностей.
- На телефоні лежать у Keychain (`AFTER_FIRST_UNLOCK`), а не в AsyncStorage.
  Keychain переживає перевстановлення, тож новий id «з нуля» так не отримати.
- «Стерти всі мої дані» (`DELETE /me`) видаляє запис, і старий токен одразу
  стає недійсним.

### Ліміти й гроші на AI
- **Денний ліміт сканів рахує сервер** за id пристрою і перевіряє його **до**
  виклику AI (`402 SCAN_LIMIT`). Раніше лічильник жив у телефоні й обнулявся
  перевстановленням.
- Ліміт частоти: `RATE_PER_MIN` (20) сканів і запитів «слова дня» на хвилину з IP.
- Створення пристроїв: **20 на годину з IP**. Достатньо для гуртожитку за
  одним NAT, але не для скрипта, який фармить безкоштовні скани.
- Справжня IP: береться запис `X-Forwarded-For`, який дописав проксі Cloud Run
  (правий, `TRUST_PROXY_HOPS`), а не перший, який пише сам клієнт. Раніше
  підміною заголовка обходились усі ліміти.
- Локальна дата клієнта (`x-local-date`) приймається лише в межах ±1 доби від
  серверної; вигадана далека дата ігнорується. День лічильника ніколи не йде
  назад: чергування «сьогодні» / «завтра» більше не обнуляє ліміт (раніше
  так проходило 14 сканів поспіль при ліміті 5; тепер це тест у
  `server/test/api.test.js`).

### Підписка
- Pro для сканів визначає **сервер**, а не телефон: вебхук RevenueCat
  (`/webhooks/revenuecat`) і, якщо вебхук загубився, власний REST-запит до
  RevenueCat із кешем на 10 хв.
- Пароль вебхука (`REVENUECAT_WEBHOOK_AUTH`) порівнюється за сталий час. Без
  заданого пароля вебхук завжди відповідає 401.
- Перенесення покупки (`TRANSFER`) забирає Pro у попереднього id; повернення
  коштів через підтримку Apple знімає Pro одразу.
- У релізній збірці без ключа RevenueCat покупки **вимкнені** (режим
  `unavailable`), а не імітуються: Pro безкоштовно ніхто не отримає.

### Стійкість сервера
- `SECURITY_HEADERS` раніше не був оголошений, і сервер **падав на першому ж
  запиті**. Виправлено.
- Кожен обробник загорнутий у `catch`: виняток дає 500, а не вбиває процес
  разом із запитами інших людей.
- Розміри тіл: `/scan` до 4 МБ (застосунок шле 150–400 КБ), вебхук до 64 КБ;
  більше дає 413. Битий JSON дає 400.
- Відповідь моделі вважається недовіреною: поля обрізаються за довжиною,
  координати рамки й контуру затискаються в 0–1000.
- Помилки Gemini/Anthropic лишаються в логах; клієнт отримує загальне «AI
  тимчасово недоступний», без деталей інфраструктури.
- Заголовки на кожній відповіді: `nosniff`, `X-Frame-Options: DENY`,
  `no-referrer`, HSTS, `Cache-Control: no-store`.

### Firestore
Сервер ходить у Firestore від імені сервісного акаунта Cloud Run (IAM).
Поки проєкт не підключений до Firebase, прямого доступу з клієнтів немає
зовсім. Якщо колись підключиш — одразу правила `allow read, write: if false;`
(готовий текст у `DEPLOY.md`, крок 3).

## Лишається як свідомий ризик

### `APP_TOKEN` — лише «лежачий поліцейський»
Він лежить у бінарнику, і витягнути його можна за вечір. Він відсікає
випадкових ботів, які знайшли URL, але не цілеспрямовану людину. Справжній
захист — ліміти за id і за IP.

### Пристрої можна фармити
Кожен новий пристрій дає 5 безкоштовних сканів на день. Зараз це стримують
20 нових пристроїв на годину з IP і Keychain, але з пулом проксі можна
наробити багато id.

**Що далі:** **App Attest / DeviceCheck** — Apple підтверджує, що запит іде
зі справжнього iPhone і нашого застосунку, а не зі скрипта. Це наступний
крок, якщо витрати на AI почнуть рости швидше за кількість людей.
Простіший запобіжник — загальна денна стеля безкоштовних сканів на весь сервер.

### Токен Pro-пристрою можна винести
Людина з jailbreak може дістати токен свого Pro-пристрою і сканувати з
нього скриптом без ліміту (його стримує лише `RATE_PER_MIN` на IP).
**Варто:** жорстка денна стеля і для Pro (напр. 300 сканів на пристрій) —
справжня людина до неї не дійде.

### Токени не відкликаються поштучно
Для анонімних id це й не потрібно: украдений токен дає лише чужі 5 сканів.
Єдиний «рубильник» — зміна `AUTH_SECRET`: вона знецінює **всі** токени, і
кожен пристрій тихо отримає нову ідентичність (лічильники скинуться, Pro
повернеться через «Відновити покупки»). Тому `AUTH_SECRET` після релізу без
крайньої потреби не міняємо.

### Ліміти словника й мов — у телефоні
100 слів і 1 мова перевіряються на пристрої, і на jailbreak їх можна обійти.
Це свідомо: вони нам нічого не коштують. Усе, що коштує грошей (скани), — на
сервері.

### Інше, не критично
- **`Access-Control-Allow-Origin: *`.** Для мобільного застосунку не
  проблема (Origin не надсилається, credentials через `*` не проходять).
  Коли з'явиться веб-версія — звузити.
- **Немає моніторингу.** Різкий стрибок сканів означає або вірусний ріст, або
  зловживання. Мінімум — бюджетний алерт у Google Cloud (`DEPLOY.md`, крок 9),
  далі Sentry і алерт на кількість `/auth/device` за годину.
- **Ліміти частоти в пам'яті одного інстансу.** Якщо Cloud Run підніме кілька
  інстансів, кожен рахує окремо. Для поточних масштабів нормально.

## Перевірка перед кожним релізом

```bash
cd ~/Documents/LinguaLens

# 1. Жодного ключа в коді застосунку (має бути порожньо)
grep -rnE "AIza|sk-ant-|sk_[A-Za-z0-9]{16,}" App.js src/ .env.example

# 2. Секрети не відстежуються git (має бути порожньо)
git ls-files | grep -E '(^|/)\.env$|\.p8$|\.p12$|server/data\.json$'

# 3. У змінних збірки лише публічне (немає sk_, AIza, sk-ant-)
eas env:list production

# 4. Тести
npm test && npm run test:server
npm audit --omit=dev

# 5. Живий сервер
URL=https://lingualens-server-….run.app
curl -s -D - -o /dev/null $URL/health | grep -iE "strict-transport|nosniff"   # заголовки на місці
curl -s -X POST $URL/scan -H 'x-app-token: ТВІЙ_APP_TOKEN'                  # → {"error":"UNAUTHORIZED"}
curl -s -o /dev/null -w "%{http_code}\n" -X POST $URL/webhooks/revenuecat -d '{}'  # → 401
curl -s $URL/health                                                          # → "store":"firestore"
```

І в браузері: [Billing → Budgets & alerts](https://console.cloud.google.com/billing)
— бюджет із попередженням виставлений.
